# Phase 03.1: Day/Night Theme - Context

**Gathered:** 2026-06-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Add a user-facing **day (light) / night (dark) theme toggle** to the currently dark-only site. This means: (1) tokenize the remaining hardcoded colors into the central `:root` design-token system so they can flip per theme, (2) design a light "day" palette that fits the dream-pop brand, (3) add a toggle control, and (4) persist the choice (localStorage) with a no-flash-before-paint init and a `prefers-color-scheme` default.

The existing **dark theme IS the night theme** — it is already built and must not change. This phase adds the light theme + the switching machinery, not a redesign of the dark look.

**Out of scope (new capabilities → their own phase):** per-section theme overrides, scheduled/auto time-based switching, additional themes beyond day/night, animation/transition redesign.

</domain>

<decisions>
## Implementation Decisions

### Light ("day") palette — direction
- **D-01:** The light palette is **not finalized in text — it will be prototyped visually and chosen by the user (design-first).** Build TWO directions to compare side by side:
  - **Clean white** (user's current lean) — light-grey/white background, airy, modern.
  - **Warm cream / paper** (Claude's recommendation) — soft off-white with warmth; best fit for the film-grain analog dream-pop mood.
  The user explicitly wants to *see* both before deciding ("я бы пытался экспериментировать… ближе чисто белый, но может стоит и рекомендацию попробовать"). This decision is deferred to the `/gsd:ui-phase` (UI-SPEC) / sketch step, NOT to the planner guessing.
- **D-02:** **Accent colour in day mode = a deeper / more saturated pink** than the night accent `#f3a9bd` (the brand pink looks washed out on a light background; darken it for contrast on buttons/links/active states). Night mode keeps `#f3a9bd` unchanged.

### Toggle — placement & form
- **D-03:** **Placement: top-right corner of the header / nav.** Conventional, always visible, doesn't overlap content or the fixed bottom now-playing bar.
- **D-04:** **Form: base is a sun/moon icon** that swaps with the active theme. ALSO prototype a **brand-themed «брусника» (lingonberry) icon variant** (e.g. a berry/sprig that reads as day vs night) during the design step — the user likes the idea of a custom brand icon. Sun/moon is the safe fallback because a theme toggle must stay instantly recognizable; user picks after seeing both.

### First-visit default
- **D-05:** **Follow the device `prefers-color-scheme`** on first visit (device in dark → show night; device in light → show day). The user's explicit toggle choice then persists in `localStorage` and overrides the system preference on later visits. No-flash-before-paint init required (per ROADMAP goal).

### Theming scope
- **D-06:** **Full theming — no "dark islands."** The light theme recolours background, text, surfaces/cards, the now-playing player bar, AND modals — everything is consistent in day mode. Not just background + text.

### dream-pop effects in light mode
- **D-07:** **Keep the film-grain texture and cursor-follow glow in the light theme, but softer / subtler** so the dreamy atmosphere survives without looking dirty or harsh on a light background. Do not remove them; do not keep them at full dark-mode intensity.

### Claude's Discretion
- Exact token architecture (how the second palette is scoped — `[data-theme]` attribute vs class, `:root` defaults + override block), the no-flash inline-script implementation, transition timing on toggle, and the precise hex values within each chosen direction are implementation details for research/planning/UI-SPEC.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `src/styles/global.css` `:root` — 12 colour tokens + font tokens already centralized. Many components already consume `var(--color-*)`, so those flip for free once a second palette is defined. Extend here.

### Established Patterns
- Components use CSS custom properties (`var(--color-accent)` etc.) for the colours that ARE tokenized — the right pattern to lean on. New per-theme values plug into the same variable names.
- No-flash theme init pattern: a tiny inline `<script>` in `<head>` (`src/layouts/Layout.astro`) that sets the theme attribute from `localStorage` (or `prefers-color-scheme`) before first paint — standard for this kind of toggle.

### Integration Points / Work Estimate
- **~92 hardcoded hex/rgba colours across ~10 components** (`ShowsSection`, `HeroSection`, `TracksSection`, `AboutSection`, `GallerySection`, `AudioPlayer`, `FooterSection`, `FeaturedAlbumSection`, `SingSection`, `Layout`) are NOT yet tokenized. Tokenizing these — so they can flip per theme — is the **bulk of the effort** in this phase, separate from designing the palette. Many are rgba black/white overlays and glow/gradient values that need theme-aware tokens.
- **No theme infrastructure exists yet** — no `data-theme`, no `prefers-color-scheme` handling, no `localStorage` theme key. Greenfield: toggle control + state/persistence + no-flash init are all new.
- Theme switching must reach the now-playing player bar (`AudioPlayer.astro`) and the overlay/modal components (lessons modal, video modal, PhotoSwipe) per D-06.

</code_context>
